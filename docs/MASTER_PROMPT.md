### 1.2 Decisión arquitectónica ADR-001 (propuesta)

**Evolución con refactorización modular del núcleo**. Mantener Node.js LTS soportado, Express soportado, EJS SSR, MongoDB/Mongoose compatible, CSS compilado y JS/TypeScript según costo de introducción. Reutilizar estilos, vistas, assets autorizados, catálogo, slugs y navegación que pasen pruebas. Reconstruir servicios de inventario, checkout, pagos, personalización, archivos privados, reseñas y notificaciones; extraer gradualmente lógica de los routers. No mantener dos motores de checkout activos en producción.

Comparativa preliminar por esfuerzo (horas-persona orientativas, no mediciones ni cotización):

| Paquete | Refactor | Desde cero |
|---|---:|---:|
| Auditoría, migración, arquitectura y seguridad inicial | 32–56 | 40–72 |
| UX/CMS, catálogo, admin, responsive | 52–88 | 96–156 |
| Inventario, carrito, pedidos, clientes y checkout | 72–120 | 84–140 |
| Configurador 2D y taller | 96–168 | 96–168 |
| Pagos, envíos, WhatsApp y Google | 80–144 | 80–144 |
| Valoraciones, SEO, analítica | 40–72 | 44–80 |
| QA, despliegue, restauración y manual | 56–96 | 72–120 |
| **Total técnico estimado** | **428–744** | **512–880** |

Diferencia de escenarios en punto medio: 586 frente a 696 horas, ~16% menos esfuerzo estimado. Supuestos: una tienda, español, DOP, configurador 2D con plantillas provistas, una pasarela, una logística integrada o tarifas manuales, WhatsApp y Google sujetos a acceso, sin 3D ni ERP. No incluye esperas de certificación, branding, fotografía, carga masiva de catálogo real, costos de terceros ni rediseños por cambio de alcance. Reestimar tras baseline y spike. Costo de desarrollo = horas estimadas × tarifa interna + contingencia explícita (propuesta 15–25% sobre esfuerzo no resuelto, sin duplicar reservas) + terceros aprobados. No prometer precio fijo sin validar alcance y presupuesto. Reescritura solo si el baseline demuestra incompatibilidad grave, inviabilidad de migración segura, o que el refactor supera el costo/riesgo de la alternativa; registrar ADR comparativo y pedir aprobación. No cambiar a Laravel solo por preferencia del desarrollador.

## 3. Arquitectura e infraestructura (ARC-01 a ARC-07)

- [ ] ARC-01 Monolito modular SSR + endpoints JSON internos versionados (`/api/v1`) para configurador, carrito, cotización, admin e integraciones; no microservicios prematuros. Módulos: auth, catalog, media, personalization, inventory, cart, pricing, checkout, orders, payments, fulfillment, customers, reviews, CMS, integrations, analytics, audit, jobs. Separar rutas/controllers, schemas de validación, services/domain, repositories, adapters, views y workers; negocio no reside en EJS ni en JS del navegador.
- [ ] ARC-02 MongoDB replica set/Atlas con soporte de transacciones, índices y migraciones versionadas; transacciones breves con retries acotados, sin llamadas externas dentro de ellas. Local y CI usar replica set real, no mocks de concurrencia. Verificar plan de Atlas elegido soporta operaciones/backup requeridos; si no, usar dedicado o replica set administrado. No exponer puerto DB a Internet.
- [ ] ARC-03 Almacenamiento compatible S3/R2 mediante adaptador. Buckets separados público y privado, entorno separado, metadatos en DB, URLs firmadas de vida corta, CDN para catálogo. `LocalStorageAdapter` solo local, almacenamiento privado fuera de `public`. No almacenar fotos base64 en pedidos, sesión o logs.
- [ ] ARC-04 Worker durable con outbox en Mongo y leasing atómico, reintentos exponenciales con jitter, límite, dead letter, replay autorizado, reconciliación. No depender de timers de un proceso web. Redis/cola dedicada solo si métricas lo justifican. Jobs independientes de entrega web y sin datos personales innecesarios.
- [ ] ARC-05 Entorno reproducible Docker Compose: web, worker, reverse proxy cuando proceda, DB local replica set, almacenamiento local/S3 de pruebas. Dockerfile multistage, usuario no root, versiones pinneadas, lockfile, `npm ci`, CSS compilado, health/readiness. `.env.example` documentado sin secretos. Aplicación inicia tras comprobar configuración/DB; seed explícito y no destructivo, sin cuentas demo en producción.
- [ ] ARC-06 Hosting: desarrollo y staging aislados en VPS Linux Contabo existente si se verifica capacidad, con Docker, red/volúmenes/credenciales independientes, límites y subdominio no indexable. Producción preferida: VPS Linux dedicado en costa este de EE. UU. (4 GB RAM/2 vCPU como hipótesis inicial para app + worker con DB separada; medir), Cloudflare DNS/TLS/CDN/WAF según plan, Nginx/Caddy, MongoDB Atlas y R2. Cotizar costos actuales y comparar backup, SLA, regiones, latencia RD y titularidad. No instalar en Windows/XAMPP por defecto. No comprometer recursos compartidos sin medir. Sin PaaS de disco efímero con uploads locales.
- [ ] ARC-07 Contratos de adaptadores `PaymentProvider`, `ShippingProvider`, `StorageProvider`, `MessagingProvider`, `GoogleReviewsProvider`, `EmailProvider`. Interfaz de capacidades declaradas, timeouts, errores normalizados, circuit breaker cuando aplique. Implementar sandbox y fallback controlado, no fingir que todos ofrecen webhooks, cotizaciones, reembolso o etiquetas. Configuración externa por entorno, no tokens en UI. Logs/metrics/tracing con correlation ID.

### 3.1 Modelo de datos mínimo y contratos

Usar IDs opacos estables, timestamps UTC, schemaVersion y referencias verificadas. No usar posición de array, etiqueta o slug como identidad de variante. Dinero entero en centavos DOP (validar safe integer, sin float para cálculos; migración exacta con revisión de valores fuera de dos decimales). Cantidades enteras positivas. Redondeo monetario determinista a centavos; impuestos/descuentos proporcionales reparten residuos sin perder centavos. Atributos históricos copiados inmutables. Añadir índices explícitos y constraints lógicos en servicios/transacciones; en Mongo no hay FK automática.

| Entidad / colección | Datos e invariantes esenciales |
|---|---|

## 6. Inventario, precios y carrito (INV-01 a INV-05, CART-01 a CART-04)

- [ ] INV-01 Cada SKU físico tiene onHand, reserved, available; `onHand >= reserved >= 0`. Tipo stock (pieza existente) o bajo pedido solo con capacidad/plazos aprobados; por defecto inventario físico, no aceptar ventas ilimitadas. Pieza base de joyería personalizada reserva el SKU correspondiente, no un stock distinto ficticio. Si dos productos comparten materia prima, definir SKU base/BOM únicamente con reglas confirmadas; no duplicar existencias.
- [ ] INV-02 Al carrito NO descontar ni reservar por defecto. Checkout suma cantidades por SKU incluso si diseños diferentes. Una transacción verifica y crea order + reservas + cupón reservado + outbox; updates condicionales por disponibilidad. Propuesta reserva inicial 30 min para pago online, plazo específico para transferencia/manual (propuesta 24h, confirmación comercial); job de expiración libera solo reservas activas, nunca una consumida. No usar `Math.max(0, stock-qty)` para ocultar sobreventa. Retener stock mientras pago está en verificación solo mediante regla acotada y reconciliación.
- [ ] INV-03 Cuando pago se verifica y se acepta pedido, transacción consume reserva (`onHand -= qty`, `reserved -= qty`) y registra movimiento único. Pago contra entrega, si se habilita, consume al confirmar pedido autorizado, no al carrito. Si cobro tardío tras liberar reserva, intentar reasignar atómicamente; si no hay stock, estado de excepción y reembolso/atención con autorización, nunca confirmar venta imposible. Para personalizado con depósito (si se aprueba) definir umbral y saldo; la política por defecto es pago total. No liberar inventario por un webhook fallido posterior a pago confirmado.
- [ ] INV-04 Cancelación antes de consumo libera reserva; después de consumo solo repone con movimiento autorizado si pieza está físicamente reutilizable. Personalizado fabricado no vuelve a stock vendible automáticamente; devoluciones en cuarentena, inspección y disposición. Reembolso financiero no implica reposición automática. Idempotencia por evento y línea.
- [ ] INV-05 Auditoría y reconciliación diaria de saldo, reservas, movimientos, pagos y pedidos; alerta ante invariantes rotas. Ajustes manuales requieren actor/motivo y permiso; no corregir diferencias modificando historial. - [ ] CART-01 Carrito anónimo por token/sesión seguro, persistente por plazo configurable; cliente puede recuperar por sesión autorizada. Registro/cuenta opcional no obligatorio para checkout; si se incorpora, fusionar solo carritos propios con política determinista, verificar stock/precios y no mezclar diseños. Versionado para dos pestañas; no pisar actualizaciones concurrentes.
- [ ] CART-02 Precio en centavos: `unit = precio SKU vigente + extras válidos`, `lineGross = unit × qty`, descuentos elegibles según regla y base, subtotal/descuento/impuesto/envío separados, `total = subtotal - descuentos + impuestos no incluidos + envío`, nunca negativo. Si precios incluyen ITBIS no sumar de nuevo; desglosar según política fiscal aprobada por contable. Definir aplicación sobre extras/envío y redondeo con ejemplos; no fijar tasa fiscal sin validación. Costo logístico no es margen de producto.
- [ ] CART-03 Ofertas: precio anterior real y superior al actual, vigencia y zona horaria, promoción/cupón con límites, stock, exclusiones, no acumulación por defecto salvo configuración explícita; elegir prioridad determinista. Evitar cupones repetidos con contacto no verificado; definir política de identificación.
- [ ] CART-04 Cotización server-side con ID, version, vencimiento y desglose. Recalcular en checkout y comparar; si precio, diseño, disponibilidad o envío cambian, mostrar diff y solicitar reconfirmación, no cobrar importe distinto. No aceptar total cliente. Pago usa snapshot confirmado, no precio mutable. Si falla checkout preservar carrito; limpiarlo solo después de orden durable, permitir reintentar pago de esa orden.

### 7.1 Máquina de estados (nombres canónicos propuestos)

| Eje | Estados | Reglas de transición |
|---|---|---|
| Pedido | `awaiting_payment`, `confirmed`, `in_fulfillment`, `fulfilled`, `cancel_requested`, `cancelled`, `exception` | confirmed solo por condición de pago/COD e inventario; fulfilled cuando entrega/retiro de todas líneas cumplido; exception requiere atención, no equivale a cancelación; cancelado solo tras resolver stock/pago/logística. |
| Pago (por intento) | `created`, `pending`, `authorized`, `captured`, `failed`, `expired`, `voided`, `partially_refunded`, `refunded`, `disputed`, `unknown` | proveedor verificado, monotonicidad; autorización no es captura; unknown consulta/reconciliación; disputa congela decisiones financieras/taller según estado; agregados por ledger, no por última notificación. |

Estado de pago agregado: `unpaid`, `partially_paid`, `paid`, `partially_refunded`, `refunded`, `disputed`, `exception`, derivado de importes capturados menos reembolsos y ajustes aceptados. Para devoluciones posteriores a entrega conservar historial fulfilled y registrar retorno/reembolso; no borrar entrega. Transiciones fuera de orden se registran y reconcilian sin retroceder estado legítimo. No usar estados de WhatsApp como estados de pago/entrega.

## 14. Rutas y contratos de API propuestos

Conservar URLs públicas `/`, `/shop`, `/product/:slug`, `/cart`, `/checkout`, `/admin/...` donde sea viable y redirect de cambios. Rutas exactas se aprueban en OpenAPI o contrato versionado, no crear duplicados sin propósito. Todas las mutaciones requieren validación, autorización, idempotencia donde aplique y CSRF si sesión. Errores normalizados `{code,message,fieldErrors,correlationId}` sin PII ni stack. Usar 400/422 para datos inválidos, 401/403 para auth, 404 sin enumeración, 409 para versión/precio/stock, 429 para límites, 503 para dependencia temporal.

## 18. Decisiones comerciales y dependencias que deben resolverse antes de activar cada módulo

Estos puntos no están definidos por los documentos. El agente puede avanzar con defaults conservadores y flags, pero no convertirlos en contratos ni inventar valores. Registrar responsable, fecha y decisión.

| Dato/decisión | Default seguro de desarrollo / gate |
|---|---|
| Versión desplegada y datos reales | solo ZIP auditado; staging sintético, pedir repo/backup/acceso autorizado para migración |
| Branding, logos por posición, video, fuentes/licencias, FB URL | preservar assets autorizados y copy; bloquear sustitución final sin confirmación |
| Máquinas de grabado, materiales, dimensiones físicas, formatos y resolución, fuentes compatibles, tipos de producto y límites | plantilla 2D aproximada, no prometer salida lista para máquina; taller aprueba muestras y especificaciones |

| Pago total/depósito, COD, cambios, cancelación, devoluciones/garantías | pago total personalizado; depósito y COD desactivados hasta aprobar; política legal antes de publicar |
| Fiscalidad ITBIS incluido/excluido, NCF/e-CF, comprobantes | contable/asesor define; no emitir factura fiscal simulada ni asumir tasa |
